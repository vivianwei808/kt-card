# L-13 约束四件套与统一返回结构

> 确定性、可定位、可建议、互相独立；每条约束返回编号、级别、证据、建议。

## 机制

- 所有检查实现同一个接口：check(request, plan) 返回 ConstraintCheckResult。
- 返回六个字段：code、name、severity、passed、evidence、suggestions。
- 证据是列表：一条约束能同时报多个问题，逐项列出来，下一轮一次改完。
- 建议是列表，带方向带数字：「将龙井课程民宿替换为每晚不超过 700 元的酒店」。
- 评审员只有一行 map：加第五条检查等于往列表里多放一个实现，review() 不用改。
- 互相独立：每条只检查一件事，Loop 才能精确知道修好了几条、还剩几条。
- passed = suggestions.isEmpty()：还有未消化的建议就不算通过。

## 代码落点

- `TripPlanConstraint.java`：统一接口
- `ConstraintCheckResult.java`：六字段返回
- `TripPlanConstraintReviewer.java`：checks.stream().map(...)

## 复用清单

- 任何规则引擎都先定统一返回结构，再写具体规则。
- 证据要写到「哪一天、哪一项、差多少」，否则下一轮只能猜。

## 面试一句话

我的七条检查共用一个接口和一份返回结构，加规则不改调度器，报告可以直接变成返工单。

## 常见坑

每条检查自己发明返回格式。页面、反馈、测试各写一套解析，后面无法维护。
