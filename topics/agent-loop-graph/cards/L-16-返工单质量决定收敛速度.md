# L-16 返工单质量决定收敛速度

> 反馈越具体，下一轮搜索空间越小；返工单在写检查那一刻就决定了。

## 机制

- 只说「不合格」，模型要在所有可能方案里重新搜索，和没有反馈差不多。
- 「预算超 320 元，酒店每晚限价 700」把搜索压到「换一档住宿、其余不动」这个极窄子集。
- 一次全说：整份清单原样交给下一轮。一条一条修会导致费用翻倍，还会打地鼠。
- 保护已做好部分：四段 Prompt 带上上一版完整 TripPlan，并要求「保留已合格部分，逐项修复，返回完整修订版」。
- 反馈层只做搬运和排版，不改写建议文本。返工单的质量由上游每条检查的 suggestions 决定。
- 自检标准：看完这段反馈，模型的改动自由度还剩多少？余地很大说明还能写得更具体。

## 代码落点

- `PlanChatService.buildPrompt() L84-L96`：四段结构与保留要求
- `TravelPlanningEngine`：feedback = String.join，原文直连
- `ConstraintCheckResult.suggestions`：返工单的原料

## 复用清单

- 把「反馈」当成产品来设计：带位置、带数字、带方向。
- 不要在反馈层二次改写，原样搬运能保证责任可追溯。

## 面试一句话

反馈质量在写检查那一刻就决定了；好的返工单是对下一轮搜索空间的压缩。

## 常见坑

反馈只写「不符合要求，请重新生成」。模型只能重掷骰子。
