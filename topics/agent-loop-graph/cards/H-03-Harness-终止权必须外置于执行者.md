# H-03 Harness：终止权必须外置于执行者

> 挽具不削弱马力，只让力量可用；三个跨领域案例指向同一个结论。

## 机制

- Erlang/OTP 的 Let it crash：进程不管自己死活，重启还是放弃由 Supervisor 决定。内存损坏的进程无法可靠判断自己是否正常。
- 金融熔断：闪崩时每个算法单独看都理性，合起来导致市场崩溃；暂停键由不参与交易的系统按。
- 铁路信号 Fail-safe：默认红灯，确认安全才放行。断电、断通信，默认动作都是停。
- 映射到 Agent：护栏的默认姿态是「不允许继续，除非主动确认安全」，检查点站在花钱那一步的门口。
- 模型在第五轮想「再试一次」，和交易员亏损时想「再等等看」，是同一种行为。最该停的时刻，执行者的判断最不可信。

## 代码落点

- `LoopGuardrail.beforeRound()`：每轮花钱前检查
- `TravelPlanningEngine`：检查点在 generate 之前
- `PreNodeGuard`：节点级前置检查

## 复用清单

- 把「继续」写成需要主动确认的动作，默认值是停。
- 控制逻辑与执行逻辑放在不同类里，代码路径物理隔离。

## 面试一句话

终止权必须交给没有沉没成本、且看得见账单的外部程序；这是 Harness 的核心思想。

## 常见坑

让执行者自己 try-catch 自愈。它正处在错误状态，判断本身不可信。
