# I-04 SSE 选型：判据先行，技术后行

> 单向、纯文本、穿普通网关、断线自动重连，四条全中。

## 机制

- 轮询：自己给骑手打电话。打太勤占线，打太稀饭凉了，延迟与空转是一对死结。
- WebSocket：拉专线。双向能力很强，但拉线、养线、重连都要自己维护，多出来的能力要你养。
- SSE：骑手主动发消息。手机只要会收，断了自己重拨。
- 把需求翻译成判据再逐个打勾：方向单向、内容纯文本、穿普通网关、断线自愈。
- 判据先行，技术后行。先写下你在乎什么，再看谁满足。
- 选型结论要能解释「为什么不选另外两个」，而不是只列优点。

## 代码落点

- `SsePlanningEventSink`：SSE 推送实现
- `GraphViewController / PlanController`：事件流端点
- `web/src/App.tsx`：EventSource 消费与重连

## 复用清单

- 做技术选型先写判据，再看候选；把「不选它的理由」写进文档。
- 单向进度类场景优先 SSE，双向协作才考虑 WebSocket。

## 面试一句话

我按四个判据选 SSE：单向、纯文本、过网关、自愈；WebSocket 的能力我们用不上，但维护成本要自己扛。

## 常见坑

因为 WebSocket 更「高级」就选它。多出来的双向能力会变成长期维护负担。
