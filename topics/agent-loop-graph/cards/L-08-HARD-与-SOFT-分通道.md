# L-08 HARD 与 SOFT 分通道

> 硬约束决定能不能交付，软偏好决定好不好；软的不阻塞，硬的进返工单。

## 机制

- HARD：违反了就不可交付。超预算、闭馆日、时间冲突、必去项缺失。判定是布尔值。
- SOFT：违反了变差但仍可用。路线不够顺、节奏偏紧。有程度，可以给建议。
- 把「路线要顺」当硬约束，Loop 会为它反复重排直到轮次耗尽。
- 真实运行里 C5、C7 红着，系统仍然交付，页面写「规划完成」。底线守住了，建议照样展示。
- 代码只有一处判断：severity == HARD 的失败建议才进 problems。优先级由通道决定，不由模型自觉。
- 用户明说的偏好（必去景点）按硬约束处理；系统推测的偏好才是软的。

## 代码落点

- `ConstraintSeverity`：HARD / SOFT
- `TravelPlanningEngine`：只有 HARD 进返工单
- `TripPlanConstraintReviewer`：七条结果原样进报告

## 复用清单

- 每条标准先回答：不通过时，应该阻断交付还是只提醒？
- SOFT 项永远不参与停止条件，只参与展示。

## 面试一句话

我把标准分成硬约束和软偏好：硬的决定能不能交，软的决定交得好不好；混在一起会导致无限返工。

## 常见坑

把所有不满都写成硬约束。系统会为一个锦上添花的点耗尽预算。
