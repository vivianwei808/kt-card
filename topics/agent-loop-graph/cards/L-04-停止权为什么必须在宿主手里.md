# L-04 停止权为什么必须在宿主手里

> 模型没有资源观、不掌握业务标准、还存在取悦倾向，三个理由决定它不能决定停不停。

## 机制

- 理由一：模型不知道花了多少 token、用户等了多久、月度预算是多少。它的目标是「把回答做好」，不是「在预算内做好」。
- 理由二：「合格」由业务定义，写在验证器里，属于程序的知识。
- 理由三：模型被训练成给出令人满意的回答。问它「完成了吗」，它倾向说「是的」。
- 反例：把 needAnotherRound 放进 JSON 输出并决定循环生死。偏乐观会交付不合格结果，偏悲观会永远停不下来，bug 还无法复现。
- 正确做法：模型可以说「我觉得还差点什么」，记进事件流；决定循环生死的必须是评审结果和护栏。
- 模型可以提供信息，不能持有控制权。

## 代码落点

- `TravelPlanningEngine`：for 轮次，停止条件在 Java 代码里
- `RevisionPolicy`：业务侧的修改权限，也不交给模型
- `LoopGuardrail`：资源侧的停止权

## 复用清单

- 任何让模型输出「是否继续」字段的设计，都要把该字段降级为建议。
- 把循环条件写成可测试的布尔表达式，而不是模型输出。

## 面试一句话

模型可以提供继续或停止的建议，但控制权必须在宿主；这是可复现性的前提。

## 常见坑

用 Prompt 让模型输出 STOP。它可能输出任何变体，也不能为账单负责。
