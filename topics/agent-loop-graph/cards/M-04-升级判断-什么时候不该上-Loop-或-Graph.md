# M-04 升级判断：什么时候不该上 Loop 或 Graph

> 先证明一次调用不够，再证明 while 不够；每一步升级都要同时说清收益与治理代价。

## 机制

- 一次调用够用的条件：结果可一次生成、不依赖外部事实、错了用户能直接重来。三条全中就别做 Agent。
- 升 Loop 的信号：需要外部事实、需要在失败后带反馈重做、需要有限停止。
- 升 Graph 的五个信号：有本可并行的独立耗时任务；分支多到 if-else 难读；不同失败需要不同返工范围；流程要停下来等人；团队需要看见并测试结构。
- 图化的代价要一起入账：共享状态、增量合并、汇合条件、超时、取消、迟到结果，全都要设计。合同没写清，只是把复杂度搬进执行器。
- 短、直、单线程的流程，继续用清晰的 while 反而更简单。

## 代码落点

- `第3章`：一条 String answer = llm(question)，零轮次
- `第4章`：while 串行 Loop，停止条件在宿主
- `第9章`：GraphDefinition 声明节点与边，LightGraph 执行

## 复用清单

- 做技术选型汇报时，先讲「什么情况下不需要」，再讲「我们为什么需要」。这是加分答法。
- 评估升级成本时，把治理成本列成清单，和收益放在同一页。

## 面试一句话

Graph 的主收益是可维护性和可测试性，提速只是副作用；如果依赖不复杂，我会继续用 while。

## 常见坑

把「用了更复杂的架构」当成绩。架构复杂度要能被业务收益买单。
