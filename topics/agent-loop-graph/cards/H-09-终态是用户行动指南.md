# H-09 终态是用户行动指南

> SUCCESS 看结果，GUARDED 放宽条件，INFEASIBLE 改需求，UNSUPPORTED 换工具，CANCELLED 重新决定。

## 机制

- SUCCESS：HARD 全过。SOFT 有红也算成功，附黄色建议。不完美不等于不合格。
- GUARDED：尽力了但未达标，被护栏拦下。必须说清哪道护栏、差多少、下一步怎么改。
- INFEASIBLE：需求本身不可满足，零成本预检识别，用户改需求即可，属于「留客」。
- UNSUPPORTED：产品边界外，换工具或人工处理，属于「送客」。
- CANCELLED：用户主动停止，返回最好一版。
- AWAITING_USER：等待用户决定，第九章把它做成图内节点。
- 终态标签的价值在于用户读完知道下一步做什么。

## 代码落点

- `PlanningTerminalState`：六个终态
- `TravelPlanPreflight`：INFEASIBLE / UNSUPPORTED 的零调用识别
- `PlanResponse`：terminalState 与 stopReport

## 复用清单

- 给每个终态写一句「用户下一步」，写不出来说明这个终态没设计完。
- 把 HTTP 状态码的思路搬过来：粗粒度失败信息在复杂系统里不够用。

## 面试一句话

我的终态按「用户下一步该做什么」组织，不是按技术原因组织。

## 常见坑

所有失败都返回「生成失败，请重试」。用户重试后得到同样结果，进入死循环。
